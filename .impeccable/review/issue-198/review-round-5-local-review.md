## Findings

1. **Medium — module import failure escapes recovery.** Evaluate imports its module before the `OnAfterRenderAsync` try/catch and caches the failed task, so a transient failure faults the lifecycle rather than displaying a usable retry. The drawer's `Lazy<Task<IJSObjectReference>>` import and first `open` invocation have the same unprotected initialization pattern. Explicit owned retry must clear only the corresponding failed initialization attempt, not a newer owner's work. Optional focus/scroll effects also need bounded failure handling without falsely claiming mandatory guard/storage readiness.
2. **Medium — failed attachment is marked successful.** Evaluate assigns attached owner/finder before awaiting `attach`. On failure, subsequent renders skip installation and Retry storage reads through a guard that may never have attached. Attachment markers must publish only after success with current owner/finder checks, while retries remain explicit to prevent automatic render/error loops.
3. **Medium — retained Evaluate snapshot shape is insufficiently checked.** `if (value.pending)` skips missing/falsy values while `pending !== null` marks them pending. Kind-specific subject/version/text and assignment-owner coherence are also unchecked. Restore must distinguish explicit null from a valid object and reject invalid shapes before publishing storage-ready state, preserving retained bytes and operation identity on rejection.
4. **Medium — nullable drawer deserialization can crash recovery.** An outer object with `Kind=AddEvaluationNoteInput` and `Payload="null"` deserializes to null and dereferences `add.Content`; explicit null content can subsequently fail draft `.Length` checks. The outer envelope, recognized kind, nonnull typed payload and existing input constraints need validation before restoring UI state. Replay should reuse the validated parse rather than repeat null-forgiving deserialization. This is recovery robustness; it does not imply a server authorization bypass.
5. **Capture-scope location — inapplicable as a requested code change on inspected evidence.** The stable capture key deliberately uses authenticated user and club; authority ownership also includes administrator role. Both surfaces append campaign and participant and consume the same capture scope. That distinction preserves recovery through role changes while refreshing capabilities. The repeated fully-qualified claim lookups alone do not violate a mandatory convention found in the applicable guidance. The full suppressed text was unavailable through the implementer's retrieval, so this disposition is explicitly grounded in the supplied location and inspected behavior, not an invented review allegation.
